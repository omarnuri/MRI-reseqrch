# Аудит собственного кода (не старого ноутбука)

`docs/bug-ledger-2026-07-27.md` — про дефекты старого ноутбука. Этот документ про
дефекты **нового** кода: что я нашёл в `spinelab/`, когда прошёл по нему заново
после того, как заработала аксиальная ветка. Три бага настоящие, один из них —
серьёзный.

Метод: чтение всех модулей + автоматическая проверка AST (неиспользуемые импорты,
пустые `except`, изменяемые значения по умолчанию, длина функций) + контрактные
тесты, которые прогоняют **каждый** этап на пустом рабочем каталоге и на
синтетическом фантоме.

---

## 🔴 A1. Регистрация выравнивала центры кадров, а не анатомию

**Где:** `spinelab/registration.py`, `rigid_register`.

**Что было:** начальным приближением служил
`CenteredTransformInitializer(..., GEOMETRY)`, то есть совмещение геометрических
центров двух изображений.

**Почему это плохо именно здесь:** у серий этого исследования разные поля обзора —
340 мм (сагиттальная T2), 320 мм (коронарный STIR), 250 мм (аксиальная T2).
Совмещение центров кадров сдвигает изображения друг относительно друга на
сантиметры **до** начала оптимизации. Последствия:

* «поправка на движение» в отчёте отсчитывалась от неверной начальной точки;
* защита «сдвиг >15 мм — это провал оптимизации» срабатывала бы на нормальных
  прогонах и отклоняла бы корректный результат;
* при отклонении поправки код возвращал это же центрирующее преобразование как
  «выравнивание по заголовкам DICOM» — чем оно не является.

**Исправлено:** начальное преобразование — тождественное (`Euler3DTransform()` с
центром вращения в физическом центре целевого изображения). Тождественное
преобразование в SimpleITK и означает «совмещено так, как говорит геометрия
DICOM», потому что origin/direction/spacing берутся из самих изображений. Теперь
отчётный сдвиг — это действительно поправка относительно заголовков, а порог
правдоподобия имеет смысл.

## 🟠 A2. Тип преобразования после оптимизации может быть другим

**Где:** там же, разбор результата.

**Что было:** `sitk.Euler3DTransform(transform)` в предположении, что
`ImageRegistrationMethod.Execute` вернёт тот же тип, что был подан на вход. В
части версий SimpleITK он возвращает `CompositeTransform`, и такой конструктор
бросает исключение — то есть этап падал бы уже после успешной регистрации.

**Исправлено:** `_describe_transform` пробует сам объект, затем компоненты
композита, затем сырые параметры (6 чисел ригидного преобразования), и если ни
один вариант не читается — возвращает отказ с указанием причины вместо догадки.

## 🟠 A3. Центроиды из файла SPINEPS — в другой системе координат

**Где:** `spinelab/stages/geometry.py`.

**Что было:** кривизна считалась по координатам X/Y/Z из центроидного JSON
SPINEPS, если он есть, и только иначе — по канонизированной маске.

**Почему это плохо:** центроидный файл хранит координаты в порядке осей
**исходного** изображения вместе с кодом направления. Читать их как канонические
миллиметры — значит смешивать системы координат, а результат при этом выглядит
правдоподобно в обоих случаях: угол получается, просто не тот. Такие ошибки не
обнаруживаются глазами.

**Исправлено:** центроиды всегда считаются по канонизированной маске экземпляров.
Файл SPINEPS читается только как перекрёстная проверка того, сколько уровней он
перечисляет, и расхождение попадает в примечания.

## 🟡 A4. Номера разделов отчёта были написаны руками

**Где:** `spinelab/stages/report.py`.

**Что было:** `<h2>9. …</h2>` в тексте функций. При добавлении раздела «Надёжность»
появилось два раздела с номером 9, и я это заметил только потому, что смотрел
именно туда.

**Исправлено:** нумерация выдаётся счётчиком при отрисовке (`_h2`). Добавлен тест,
который проверяет, что номера идут подряд с единицы, и второй — что в HTML не
утекли неотрендеренные фрагменты шаблона (это уже случалось при автозамене).

## 🟡 A5. Мелочи, найденные автоматической проверкой

* неиспользуемые импорты `Path` в `stages/crosscheck.py` и `stages/muscles.py` —
  убраны;
* `stages/posterior.py::run` разросся до 171 строки — самая ответственная функция
  проекта была и самой трудночитаемой. Выделены `_resolve_threshold` и
  `_side_stats`;
* пустых `except:` и изменяемых значений по умолчанию не нашлось.

## Что теперь проверяют контрактные тесты

Эти тесты закрывают целый класс ошибок «этап упал вместо того, чтобы сказать, что
данных нет»:

| Тест | Что гарантирует |
|---|---|
| `test_every_default_stage_is_registered` | список этапов и реестр не разъезжаются |
| `test_nothing_fails_on_an_empty_workspace` | на пустом каталоге **ни один** этап не падает; все пропуски имеют причину |
| `test_report_is_produced_even_when_everything_skipped` | отчёт есть всегда, даже когда данных нет |
| `test_all_analysis_stages_run_on_the_phantom` | все счётные этапы проходят на фантоме |
| `test_stage_data_survives_a_process_boundary` | продолжение после обрыва работает: данные этапов переживают JSON |
| `test_sections_are_numbered_once_and_in_order` | нумерация разделов отчёта |
| `test_no_unrendered_template_braces_leak_into_the_html` | в отчёт не попадают куски шаблона |

Итого 160 тестов, все проходят, ~6 с, без GPU и без данных пациента.

## Что осталось непроверенным

Честный список — здесь автотесты бессильны:

1. **Три этапа сегментации** (SPINEPS, TotalSpineSeg, TotalSegmentator) и
   `crosscheck` — нужен GPU и веса. Проверяются только первым реальным прогоном.
2. **Регистрация на реальных данных.** Логика разбора преобразования протестирована,
   но качество совмещения коронарного STIR с сагиттальной T2 можно оценить только
   по фактическим числам сдвига и поворота из прогона. Именно поэтому они попадают
   в отчёт, а не остаются во внутреннем логе.
3. **Зеркальная TTA** — обмен меток сторон протестирован на фантоме, сам повторный
   прогон модели нет.
4. **Проверка подавления жира** протестирована на фантоме с явной жировой полосой.
   На реальном теле полоса под кожей содержит ещё и кожу, и частично воздух; порог
   1.3 подобран из физики (жир на STIR должен быть темнее глубоких тканей), а не
   калиброван на данных. Поэтому вывод «подавление не подтверждено» надёжнее, чем
   вывод «подтверждено».
